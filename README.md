# التوأم الرقمي لمزرعة المانجو 🥭

تطبيق ويب تفاعلي (React + Vite + Tailwind) لإدارة مزرعة مانجو على شكل شبكة
(30 صف × 60 عمود)، مع وضعين: **الإدارة والبيانات** لتسجيل بيانات كل شجرة،
و**تخطيط المزرعة** لتحديد الشجر والمروى والمصرف والطريق في كل مساحة.

## ما تم إصلاحه/إكماله في هذه النسخة

1. **مشروع Vite كامل وجاهز للنشر** بدل ملف component واحد فقط: تمت إضافة
   `package.json`, `vite.config.ts`, `index.html`, `tailwind.config.js`,
   `postcss.config.js`, `vercel.json`, وملف الدخول `src/main.tsx`.
2. **سبب فشل البناء الأساسي**: الأيقونة `Road` من مكتبة `lucide-react` غير
   موجودة أصلاً في المكتبة (لا يوجد export بهذا الاسم)، وهذا كان يوقف عملية
   الـ build بالكامل على Vercel. تم استبدالها بأيقونة `Route` الصحيحة.
3. **ربط Firebase فعلياً**: التطبيق متصل مباشرة بمشروع Firebase المخصص
   للتطبيق، ويستخدم Firebase Authentication + Firestore مع التخزين المؤقت الدائم
   عبر IndexedDB. يمكن استخدام متغيرات البيئة `VITE_FIREBASE_*` في Vercel
   لتجاوز إعدادات Web SDK المضمنة عند الحاجة.
4. **إصلاح خطأ منطقي في عرض حالة الأشجار**: كل مساحة شجرة كانت تظهر افتراضياً
   باللون الأخضر ("سليمة") حتى لو لم يتم إدخال أي بيانات لها فعلياً، رغم وجود
   رسمة "شجرة فارغة" رمادية في الكود لم تكن تظهر أبداً. الآن المساحة تظهر
   فارغة (رمادية) حتى يحفظ المستخدم بياناتها من النافذة المنبثقة.
5. **إضافة شارة صغيرة في الهيدر** توضح هل التطبيق يعمل حالياً في وضع
   "محلي 💾" أو "سحابي ☁️ (Firebase)".
6. **وضع Offline/PWA**: تم تفعيل Firestore persistent cache عبر IndexedDB،
   مع Service Worker لتحميل واجهة التطبيق بدون إنترنت بعد أول زيارة ناجحة.

## التشغيل محلياً

```bash
npm install
npm run dev
```

سيعمل التطبيق على `http://localhost:5173`.

## النشر على Vercel

**الطريقة الأسهل:** ارفع المجلد على مستودع GitHub ثم:

1. اذهب إلى [vercel.com](https://vercel.com) → New Project → اختر المستودع.
2. Vercel سيكتشف أنه مشروع Vite تلقائياً (الإعدادات موجودة بالفعل في
   `vercel.json`)، فقط اضغط Deploy.
3. (اختياري) لو عايز مزامنة سحابية بـ Firebase: من Project Settings →
   Environment Variables، أضف نفس المتغيرات الموجودة في `.env.example`
   بقيمها الحقيقية من Firebase Console، ثم أعد النشر (Redeploy).

**أو عبر Vercel CLI:**

```bash
npm i -g vercel
vercel
```

## تفعيل Firebase

هذا الإصدار متصل مباشرة بمشروع Firebase المخصص للتطبيق، ويستخدم:

- Firebase Authentication لتسجيل الدخول باسم مستخدم وكلمة مرور.
- Firestore مع التخزين المؤقت الدائم عبر IndexedDB للعمل بدون إنترنت.
- Service Worker / PWA لتحميل واجهة التطبيق بدون إنترنت بعد أول زيارة ناجحة.

### الحسابات وتسجيل الدخول

واجهة التطبيق تعرض **اسم المستخدم** و**كلمة المرور فقط**. التطبيق يستخدم Firebase Email/Password Authentication داخلياً، لكنه يحوّل اسم المستخدم تلقائياً إلى عنوان داخلي بالشكل:

```text
USERNAME@mango-farm-4b1a6.firebaseapp.com
```

لذلك لا يحتاج المستخدم إلى كتابة بريد إلكتروني.

#### إنشاء حساب

كل مستخدم يستطيع إنشاء حسابه بنفسه من زر **مستخدم جديد — إنشاء حساب** في صفحة الدخول. يجب تفعيل **Email/Password** من Firebase Console → Authentication → Sign-in method.

لكل حساب اسم مستخدم فريد وكلمة مرور مستقلة. لا يتم تخزين كلمات المرور في Firestore أو localStorage؛ يتم إدارتها بواسطة Firebase Authentication.

بعد إنشاء الحساب يتم تسجيل دخول المستخدم تلقائياً. ولا تحتاج إلى إنشاء المستخدمين يدوياً من Firebase Console إلا في حالات الإدارة الخاصة.

### ملاحظات مهمة

- لا يتم استخدام Firebase Service Account داخل المتصفح.
- إعدادات Firebase Web SDK فقط موجودة في التطبيق.
- جلسة تسجيل الدخول محفوظة محلياً في المتصفح، لذلك بعد تسجيل الدخول بنجاح يمكن استعادة الجلسة عند العمل بدون إنترنت.
- بيانات المزرعة تظل في نفس بنية Firestore الحالية لكل Firebase UID؛ لم يتم تغيير معرفات الخلايا أو بنية بيانات المزرعة.

## تحسينات عرض الخريطة (Farm map rendering)

- **الطرق والمروى والمصارف كمعالم متصلة**: لا تُخزَّن أي بيانات جديدة. الشكل يُحسب وقت العرض من نفس البيانات
  الحالية (نوع الخلية `water_canal` / `drainage` / `road`، أو عمود/صف مُعلَّم كطريق/مصرف/فراغ).
  كل خلية تُقارن بجيرانها (أعلى/أسفل/يمين/يسار) من نفس النوع، فتتصل الأجزاء المستقيمة والمنحنيات وتقاطعات T والتقاطعات
  الكاملة تلقائياً، وتُعاد الحسابات فوراً عند إضافة أو حذف أي خلية دون تعديل الجيران يدوياً.
  الرسم عبارة عن طبقة SVG واحدة فوق الأرضية (بضعة عناصر `<path>` فقط مهما كبرت الخريطة)، أما الخلايا نفسها فتبقى
  كما هي لاستقبال اللمس والتحديد والتعديل.
- **الأصناف**: كل صنف له علامة لونية صغيرة (عنقود ثمار) على الشجرة. التخصيص في `src/farm/treeVisuals.ts`
  (`VARIETY_ACCENTS`) ويعتمد على اسم الصنف المخزَّن كما هو. «غير محدد» بلا علامة.
- **حالة الشجرة**: الصحة والتقليم يبقيان حقلين مستقلين. الشجرة «تحتاج تقليم» ومعها مرض مسجَّل تظهر
  **برتقالية مع بقعة حمراء** (والبرتقالي هو الغالب)، بينما المصابة فقط تبقى حمراء بالكامل.
  لا يتم تغيير أي قيمة مخزَّنة لتحقيق ذلك.
- **الأداء**: الخلايا `React.memo` وجسم الشبكة محفوظ بـ `useMemo` (السحب/التكبير/تغيير حالة المزامنة لا يعيد رسم
  ~1800 خلية)، وهندسة الشجرة تُعرَّف مرة واحدة وتُستنسخ بـ `<use>` مع متغيرات CSS، وحركة المياه بـ CSS فقط
  (تتوقف أثناء السحب، وتُلغى عند تفعيل «تقليل الحركة» في النظام)، وتُخفى التفاصيل الدقيقة عند التصغير.
- **التحقق**: `npm run verify` يشغّل فحوصات محرك الاتصال وحالات الأشجار (يحتاج Node 22.18 أو أحدث).

## عناصر المزرعة المخصصة، الحالات الجديدة، وتحسينات الخريطة

- **حالتان جديدتان للشجرة (أسود)**: `مطعمة` و`مقلوعة` قيمتان جديدتان في نفس حقل `status` الحالي (لا حقول جديدة ولا ترحيل بيانات).
  تُرسمان باللون الأسود وتبقيان مختلفتين في البيانات. لا تُمسّ بيانات المرض أو تاريخ التقليم.
- **«تقليم» ← «ضعيفة»**: تغيير في **النص المعروض فقط** (`statusLabel` في `treeVisuals.ts`). القيمة المخزَّنة تبقى `تحتاج تقليم`،
  وحقل «تاريخ آخر تقليم» كما هو لأنه عملية تقليم فعلية.
- **حجم الأشجار والمسافات**: مقاييس الخريطة المرئية فقط في `GRID` (`infrastructure.ts`): الخلية 76×88 والفاصل 28px (تم تكبيرهما في التحديث الأخير، انظر القسم التالي). معرّفات الأشجار وإحداثياتها وترقيمها لا تعتمد على هذه الأرقام.
  عروض الطرق/المروى/المصارف تُضرب في `INFRA_SCALE` فتبقى بنفس النسبة من الخلية.
- **عناصر مخصصة (Landmarks)**: زر **«قائمة العناصر»** في «تخطيط المزرعة» (انظر القسم التالي). كل عنصر موضوع له اسم وأيقونة ومعرّف ثابت (`lm_…`)
  وموقع على **شبكة فتحات مستقلة** (`landmarks.ts`) تقع في الفراغات بين الأشجار فقط؛ لا تستبدل شجرة ولا تُنشئ صفوفاً أو أعمدة جديدة.
  إحداثياتها تُحسب من أعلى-يسار الشبكة لذلك لا تتغير عند إضافة صفوف/أعمدة.
  لا يُسمح بوضع عنصر على طريق/مصرف/مروى (خلية مجاورة طريق أو مصرف تمنع الموضع؛ بجانب مروى واحد مسموح) ولا فوق عنصر آخر.
- **التخزين (تغيير بسيط ومتوافق مع القديم)**: حقل اختياري جديد `landmarks` داخل نفس وثيقة المزرعة
  (`artifacts/{APP_ID}/users/{uid}/farm_data/gridState`)، على شكل خريطة `landmarks.<id>`. تُكتب كل عملية بمفتاح واحد (`updateDoc`)
  تماماً مثل `cells.<id>`، فالإعادة آمنة (نفس المعرّف) ولا تتعارض أجهزة مختلفة تضيف عناصر مختلفة.
  المزارع القديمة بدون الحقل تعمل كما هي. **لا تغيير في قواعد Firestore** (نفس المسار ونفس المالك).
- **الصرف**: خندق خرساني ضيّق بلون رمادي بارد وأرضية داكنة ونهايات مغلقة (جدار)، يختلف بوضوح عن الطريق (بيج عريض) والمروى (أزرق).
- **حوض الرش**: رسم SVG واحد يتمركز ويتناسب مع الخلية (لا قصّ ولا تشويه)، وبيانات الخلية (`spray_tank`) كما هي.
- **الجوال**: شريط العنوان الأخضر يختفي بانزلاق عند سحب الخريطة للأعلى ويظهر عند السحب للأسفل (لمس/قلم فقط، عتبة 28px)،
  مع مقبض صغير لإظهاره دائماً. على سطح المكتب لا شيء يتغير. اعكس الاتجاه بالثابت `HIDE_HEADER_WHEN_FINGER_MOVES_UP` في `App.tsx`.
- **التحقق**: `npm run verify` يشغّل فحوصات المحرك والحالات والعناصر المخصصة (يحتاج Node 22.18+).

## الاتجاه، الترقيم، قائمة العناصر، والأداء (آخر تحديث)

**1) عكس الخريطة** — في «تخطيط المزرعة» ← «اتجاه الخريطة»: `الاتجاه الأصلي` · `عكس أفقي` · `عكس رأسي` (اختيار مباشر وليس قلباً إضافياً).
- يُنفَّذ كتحويل عرض فقط (`farm/orientation.ts`): `(r,c)` ← أصلي `(r,c)`، أفقي `(r, C-1-c)`، رأسي `(R-1-r, c)`. لا تُمَسّ سجلات الأشجار ولا معرّفات الخلايا ولا الإحداثيات المخزّنة.
- يشمل الأشجار والخلايا الفارغة والطرق والمداخل والمروى والمصارف وأحواض الرش والعناصر المخصصة وشريطي التسميات (صف العناوين وعمود الصفوف ينتقلان للجهة المقابلة).
- يُحفظ في حقل اختياري واحد `mapOrientation` داخل نفس وثيقة المزرعة (بنفس آلية الإعدادات الحالية). غيابه = الاتجاه الأصلي.
- **إعادة ضبط الرؤية** تحسب الرؤية من الأبعاد الفعلية المقاسة للمزرعة المعروضة (`farm/viewport.ts`) فتُظهر المزرعة كاملة ومتمركزة دون تغيير الاتجاه، وتحترم حدود التكبير (0.15–3). على شاشات صغيرة جداً قد لا تتسع المزرعة كاملة عند أقل تكبير؛
  عندها تُحاذى الزاوية العلوية اليسرى **المعروضة** مع حافة الشاشة. تُطبَّق نفس الرؤية عند التحميل الأول وعند تغيير الاتجاه.

**2) الترقيم (عرض فقط)** — الصف بدون أصفار بادئة والعمود بأصفار بعرض ثابت: `1-01` · `12-07` · `30-60` (مزرعة من 100 عمود فأكثر تعرض كل الأعمدة بثلاث خانات `001`…`120`).
كان العرض `001-012`. معرّفات التخزين (`<حرف الصف>-<رقم>`) لم تتغير ولا يوجد ترحيل بيانات. كل التسميات تأتي من `farm/coordinates.ts`.

**3) قائمة العناصر (Landmark Palette)** — زر «قائمة العناصر» يفتح:
- تبويب **الأنواع**: العناصر الجاهزة (حنفية 🚰، حوض ماء 💧، عمود إنارة 💡، علامة مرافق 📍) + أنواعك الخاصة، وبجانب كل نوع **عدد ما وُضع منه**. «نوع جديد» ينشئ نوعاً (اسم + أيقونة) ثم يبدأ وضعه فوراً.
- اختيار نوع يبدأ **وضع التكرار**: اضغط على أي عدد من الفراغات بين الأشجار فيُنشأ عنصر مستقل في كل مرة (معرّف `lm_…` خاص به)، مع شريط ثابت فيه «انتهيت» و«تراجع» (عن آخر عنصر) و«نوع آخر». الأماكن غير الصالحة (شجرة/طريق/مصرف/مكان مشغول) تُرفض برسالة.
- تبويب **الموضوعة**: كل عنصر موضوع؛ الضغط على عنصر على الخريطة (أو في القائمة) يفتح تفاصيله: تغيير نوعه، ملاحظة، **نقل** (اضغط المكان الجديد)، و**حذف هذا العنصر فقط** بعد تأكيد. حذف عنصر لا يحذف بقية عناصر نوعه، ولا يُحذف نوع مستخدم.
- التخزين: عناصر قديمة بدون نوع تُحسب ضمن نوع جاهز إن طابق اسمها وأيقونتها، وإلا تُجمَّع بنوع مشتق ثابت. حقلان اختياريان جديدان فقط: `landmarkTypes.<id>` (الأنواع الخاصة) و`typeId` داخل كل عنصر. كل عملية تكتب مفتاحاً واحداً (`updateDoc`) فالمزامنة بعد الانقطاع وإعادة المحاولة لا تكرر العناصر.

**4) الأداء** — قياسات في Chromium بدون GPU (نفس المزرعة 30×60 ونفس تسلسل التكبير) أظهرت أن تكلفة الإطار كانت في الرسم وليس في React.
ما تم: خطوط الخلايا المتقطعة في وضع التخطيط كانت 1800 مخطّطاً (`outline`) فاستُبدلت بنمط SVG واحد (`EditGridOverlay.tsx`)، وحالة السحب لم تعد حالة React (لا إعادة رسم لـ `App` عند بدء/نهاية السحب)، وحسابات الاتجاه/العناصر تُحفظ بـ `useMemo` ولا تُعاد أثناء التكبير.
**النتيجة المقيسة**: في وضع التخطيط انخفضت كلفة «الرسم» لكل إطار ~38% (13.4→8.4ms) وبقي زمن الإطار الوسيط كما هو، **لكن الخريطة صارت أكبر بحوالي 40% مساحةً (طلب تكبير الأشجار والمسافات)** فعوّض ذلك أغلب المكسب؛ أي أن صافي الفرق صغير ويقع ضمن هامش القياس (±10–15%).
في وضع العرض لا فرق واضح. جُرّب `content-visibility: auto` وإزالة تلميحات الطبقة (`will-change`…) فلم يُعتمدا لأنهما لم يُحسّنا أو أبطآ. توقفات التصغير عند ~0.5 و~0.25 تتزامن مع تغيّر مقياس رسم الطبقة الكبيرة في المتصفح.
الأرقام من متصفح بدون تسريع رسومي؛ جرّب على جهاز فعلي لتحكم على السلاسة.

**5) شريط العنوان على الجوال** — الانزلاق كان 280ms (الشفافية 220ms) وصار 840ms (الشفافية 660ms) بمنحنى واحد مشترك (`--farm-header-ms` في `index.css`، ويقابله `HEADER_ANIM_MS` في `App.tsx`).
الانزلاق على الشريط نفسه (`transform`/`opacity`) والخريطة تتبع حافته، ولا يُعكس اتجاه الانزلاق خلال 320ms من الانزلاق السابق. سطح المكتب لم يتغير.

**التحقق**: `npm run verify` (5 ملفات: العرض، الإحداثيات، العناصر، الاتجاه/الرؤية، أنواع العناصر) ثم `npx tsc --noEmit` و`npm run build`.
